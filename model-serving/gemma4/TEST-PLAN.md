# Test Plan — Stand up Gemma 4 for inference serving on OpenShift

**Purpose:** Validate that the cluster can serve an open-weight LLM (Gemma 4) for
OpenAI-compatible inference. This is a **cluster smoke test**, not a customer
deliverable — single model, single Deployment, no auth/encryption.

**Result of the reference runs:** PASS in the `lazy` and `kserve` serving modes on
`api-oac-prod` (MOC/NERC OAC). Model `gemma-4` served tensor-parallel across 2× H100;
`/v1/models`, chat completions, streaming, and GPU residency all returned correctly.
- `lazy` (plain Deployment): validated 2026-08-24.
- `kserve` (InferenceService from `pvc://`, weights pre-staged by a seed Job):
  validated 2026-09-02 — `test.sh --stream --gpu` = **5/5 PASS**.
- `serverless` (Knative KPA autoscaling, scale-to-zero): autoscaling validated
  2026-09-08 (scale-to-zero + cold-start 0→1); the client-facing endpoint has a
  known cluster-edge routing caveat (§4).

All were torn down afterward to stop GPU charges.

## 1. Prerequisites (what must be true before you start)

### Access
- An account that can create/own a project namespace. We used `oc new-project`
  (the account had `projectrequests: create` but not raw `namespaces: create`).
- `oc` CLI logged in (`oc whoami` succeeds). `kubectl` was not installed — use `oc`.
- **No node-level access required.** Everything below runs at the namespace level.

### Cluster capabilities that must be present
| Requirement | How it was satisfied on the reference cluster | How to check |
|---|---|---|
| GPU nodes with NVIDIA H100 | 2 worker nodes, 4× H100 80GB each (8 total) | `oc get nodes -l nvidia.com/gpu.present=true` |
| GPU Operator advertising `nvidia.com/gpu` | NVIDIA GPU Operator (ClusterPolicy) + NFD | `oc get node <gpu-node> -o jsonpath='{.status.allocatable.nvidia\.com/gpu}'` |
| GPU pods schedulable (not Kueue-gated in this ns) | Confirmed via pre-flight pod | pre-flight (step 3.0) |
| RWX storage class | Portworx fronting Pure FlashBlade via NFS v4.1 (`pure-fb-nfsv4`, `backend: pure_file`) | `oc get sc` |
| Egress to `huggingface.co` + Xet CDN | HTTP 200 to hub; weights pull from `us.aws.cdn.hf.co` | pre-flight (step 3.0) |
| Ability to pull `docker.io/vllm/vllm-openai` | Pulled directly; no blocking ImageContentSourcePolicy | pre-flight (step 3.0) |

> **Fallback if docker.io is blocked:** RHOAI (2.25.10 here) ships a supported vLLM
> `ServingRuntime` that can be used instead of the raw docker.io image.

### The model
- **`google/gemma-4-31B-it`** — License **Apache 2.0, UNGATED** (no click-through,
  no gated-repo token permission). Repo id is **case-sensitive** (capital `B`).
- 30.7B dense params, BF16, **~62 GB weights** → too tight for one 80 GB H100 once
  the KV cache is added, so served **tensor-parallel across 2× H100**.
- HF token is **optional** (only helps download rate limits). A plain fine-grained
  **read** token is sufficient — no gated permission needed.
- Single-GPU alternative if ever needed: the QAT checkpoint
  `google/gemma-4-31B-it-qat-w4a16-ct` (~1/4 size, compressed-tensors).

### Image / software pins that matter
- Image: **`docker.io/vllm/vllm-openai:gemma4`** (CUDA 12.9). This tag bundles
  **transformers ≥ 5.5.0**, which is required to load the `gemma4` architecture.
  - Generic `:latest` **fails** with `model type 'gemma4' not recognized`.
  - `:gemma4-cu130` exists but needs a newer GPU driver than this cluster had.
- vLLM auto-selects the `TRITON_ATTN` backend for Gemma 4 (heterogeneous head
  dims); no manual attention-backend config needed.

## 2. Repo layout & resources

The manifests are a **kustomize base + components**; per-run values come from
`scripts/config.conf`. The base holds only what both serving modes share (the
Pure PVC and the tunable ConfigMap); each mode's serving mechanism is a kustomize
**component** the generated overlay selects via `SERVE_MODE`.

```
model-serving/gemma4/
  base/                 # SHARED by both modes
    kustomization.yaml  #   resources (pvc) + configMapGenerator (params.properties)
    pvc.yaml            #   PVC model-cache, RWX, pure-fb-nfsv4  (the weight store)
    params.properties   #   default vLLM args (MODEL_ID, TP_SIZE, ...)
  components/
    lazy/               # SERVE_MODE=lazy — plain Deployment, HF-on-first-boot
      deployment.yaml   #   Deployment gemma4-vllm (vLLM server)
      service.yaml      #   ClusterIP :8000
      route.yaml        #   edge-TLS Route (default cert -> curl -k)
    kserve/             # SERVE_MODE=kserve — KServe InferenceService from pvc://
      serving-runtime.yaml   #   vLLM ServingRuntime (gemma4 image, TP, /dev/shm)
      inference-service.yaml #   InferenceService, storageUri pvc://model-cache/...
      compile-cache-pvc.yaml #   RWX PVC for the shared torch.compile cache
      seed-job.yaml          #   one-shot: stage weights onto the PVC, then exit
  overlays/current/     # GENERATED by up.sh from config.conf (namespace, image,
                        #   params, component, GPU_COUNT, STORAGE_SIZE)
  scripts/
    config.conf            # <-- the ONE file you edit to set values (BF16, 2 GPU)
    config.quantized.conf  # ready-made single-GPU w4a16 variant (CONFIG_FILE=...)
    config.serverless.conf # ready-made Knative KPA + scale-to-zero variant (CONFIG_FILE=...)
    up.sh  down.sh  test.sh  benchmark.sh  lib.sh
```

> `serverless` reuses the `kserve` component (same ServingRuntime + InferenceService
> + seed Job); `up.sh` flips the InferenceService to `deploymentMode: Serverless` so
> KServe hands it to Knative. There is no separate `components/serverless/`.

**Settable values** (in `scripts/config.conf`, or as env-var overrides):
`NAMESPACE`, `SERVE_MODE` (`lazy`|`kserve`|`serverless`), `IMAGE`, `MODEL_ID`,
`SERVED_NAME`, `TP_SIZE`, `MAX_MODEL_LEN`, `GPU_MEM_UTIL`, `GPU_COUNT` (must equal
`TP_SIZE`), `STORAGE_SIZE`, `HF_TOKEN` (optional), and the autoscaling knobs
`MIN_REPLICAS`, `MAX_REPLICAS`, `SCALE_METRIC` (`cpu`|`memory` for kserve;
`concurrency`|`rps` for serverless), `SCALE_TARGET`. An alternate config file can be
selected with `CONFIG_FILE=<name>` (resolved next to the scripts) —
`config.quantized.conf` is a ready-made single-GPU w4a16 variant, and
`config.serverless.conf` is a ready-made Knative KPA + scale-to-zero variant.

### Serving modes (`SERVE_MODE`)
All three modes serve the same OpenAI-compatible API off the **same Pure RWX PVC**;
they differ in how the weights get there and what fronts vLLM. Keeping all three is
deliberate — the demo shows the *range* of what the compute center supports, from a
quick spike to a governed platform deployment to an elastic, scale-to-zero one.

| | `lazy` (default) | `kserve` | `serverless` |
|---|---|---|---|
| Front-end | plain `Deployment` + `Route` | KServe `InferenceService` (RawDeployment) | KServe `InferenceService` (Knative Serverless) |
| Weights onto PVC | vLLM pulls from HuggingFace on first boot | explicit **seed Job** stages them first | explicit **seed Job** (same as kserve) |
| Reads weights from | `HF_HOME=/cache` on the PVC | `pvc://model-cache/<model>` mounted at `/mnt/models` | `pvc://model-cache/<model>` mounted at `/mnt/models` |
| Autoscaling | none (fixed) | HPA on cpu/memory | Knative KPA on concurrency/rps, incl. **scale-to-zero** |
| Cluster requirement | none beyond GPUs + storage | RHOAI single-model serving (KServe) | + RHOAI Serverless (Knative + a Knative ingress) |
| Best for | quick iteration, minimal platform deps | governed serving + pre-staged, HF-independent weights | bursty/idle traffic; pay-for-what-you-use GPUs |

`up.sh` handles the sequencing: in `kserve`/`serverless` mode it creates the PVC,
runs the seed Job **to completion**, and only then applies the ServingRuntime +
InferenceService (so vLLM never starts against an empty `/mnt/models`). In
`serverless` it sets the annotation `serving.kserve.io/deploymentMode: Serverless`
and Knative provides the endpoint URL (no external Route created).

The vLLM string/number args flow through a `configMapGenerator` (hashed name →
any change auto-rolls the pod). `GPU_COUNT` and `STORAGE_SIZE` are resource
fields, so they're applied as JSON6902 patches in the generated overlay. All of
this uses `oc`'s built-in kustomize (`oc apply -k`) — no extra tooling needed.

### Key Deployment settings and *why* (these are the non-obvious bits a test plan needs)
- `--tensor-parallel-size=2` and `limits.nvidia.com/gpu: "2"` — 31B spans 2 GPUs.
- `--max-model-len=8192`, `--gpu-memory-utilization=0.90` — modest KV cache for a test.
- `HF_HOME=/cache` mounted to the PVC — weights persist, not re-downloaded on restart.
- **`HOME=/home/vllm` on a writable emptyDir** — OpenShift's `restricted` SCC runs a
  random high UID with `HOME=/` (not writable); without this, flashinfer/torch caches
  fail with `PermissionError: [Errno 13] ... '/.cache'` → CrashLoopBackOff.
- **Fully-qualified image** (`docker.io/…`) — CRI-O `short-name-mode=enforcing`
  rejects the bare `vllm/vllm-openai:gemma4` as ambiguous.
- `shm` emptyDir (`medium: Memory`, 16Gi) at `/dev/shm` — NCCL needs shared memory
  for the tensor-parallel collective ops.
- Startup probe budget ~20 min (`failureThreshold: 80`, `periodSeconds: 15`) — first
  run downloads ~62GB before the server reports healthy.

## 3. Stand-up procedure

### 3.0 Pre-flight (throwaway pod — verify egress, CDN, image pull, GPU scheduling)
Confirm the cluster can (a) schedule a GPU pod in this namespace, (b) reach
`huggingface.co`, and (c) actually **download** a real weight file end-to-end
(not just resolve DNS — the legacy `cdn-lfs.huggingface.co` host is dead; real
traffic goes to `us.aws.cdn.hf.co`). If the download fails, stop and arrange an
internal mirror before going further.

### 3.1 Scripted path (recommended)
```
cd scripts
$EDITOR config.conf          # set NAMESPACE, SERVE_MODE, TP_SIZE/GPU_COUNT, MODEL_ID, etc.
./up.sh                     # generates overlay, applies, waits for Ready, prints URL
```
`up.sh` creates the project if needed, creates the `hf-token` secret only if
`HF_TOKEN` is set, then:
- **lazy:** applies the overlay and blocks on `oc rollout status` (30-min timeout
  for the first weight pull).
- **kserve:** creates the PVC, runs the **seed Job to completion**, applies the
  ServingRuntime + InferenceService, publishes the external Service + Route, and
  blocks until the InferenceService is `Ready`.

Use `./up.sh --no-wait` to return without blocking. **`kserve` is strongly
recommended via the script** — it sequences the seed Job before serving so vLLM
never starts against an empty `/mnt/models`.

### 3.2 Manual path (no scripts)
The `base/` alone only creates the shared PVC + ConfigMap — it does **not** stand
up a server. Apply the mode-selecting overlay that `up.sh` generates:
```
oc apply -k overlays/current                      # lazy: this is the full stand-up
```
For `kserve` manually you must run the seed Job to completion **first** (see the
seed step in `up.sh`), then `oc apply -k overlays/current` and create the external
Service + edge Route.

### 3.3 Watch it come up (first run pulls weights → several minutes)
```
oc get pods -n eldritchjs-sandbox -w
# lazy:
oc logs deploy/gemma4-vllm -n eldritchjs-sandbox -f
# kserve (seed first, then predictor):
oc logs job/gemma4-seed -n eldritchjs-sandbox -f
oc logs deploy/gemma4-predictor -n eldritchjs-sandbox -f
```
Pod goes `ContainerCreating` → `Running` (not-ready while downloading) → `Ready`.

## 4. Verification / success criteria

**Automated:** `cd scripts && ./test.sh` runs checks 1–3 below and prints
`PASS/FAIL` (exit non-zero on any failure). Add `--stream` and `--gpu` for the
streaming and GPU-residency checks. `test.sh` is **mode-aware** — it resolves the
right route and pod label from `SERVE_MODE`, so the same command works for both.

The manual commands below use the **`lazy`** route/label. In **`kserve`** mode the
names differ (test.sh handles this for you): route `gemma4-infer` (deliberately
*not* named `gemma4` — a route sharing the isvc's name gets pruned by KServe while
it reconciles), pod label `serving.kserve.io/inferenceservice=gemma4`, and vLLM
listens on `8080` internally (fronted by the external Service + edge Route on 443).

```
# lazy:
URL="https://$(oc get route gemma4-vllm -n eldritchjs-sandbox -o jsonpath='{.spec.host}')"
# kserve:
URL="https://$(oc get route gemma4-infer -n eldritchjs-sandbox -o jsonpath='{.spec.host}')"
```

| # | Check | Command | Pass condition |
|---|---|---|---|
| 1 | Pod healthy | `oc get pod -l app=gemma4-vllm -n eldritchjs-sandbox` | `Running`, `READY 1/1` |
| 2 | Model listed | `curl -sk "$URL/v1/models"` | HTTP 200; `id: gemma-4`, root `google/gemma-4-31B-it`, `max_model_len 8192` |
| 3 | Inference | `curl -sk "$URL/v1/chat/completions" -H 'Content-Type: application/json' -d '{"model":"gemma-4","messages":[{"role":"user","content":"Write a Python function that reverses a linked list."}],"max_tokens":300}'` | coherent, on-topic code in `choices[0].message.content` |
| 4 | Streaming | add `"stream":true` to the body, `curl -Nsk` | `data: {...}` SSE chunks ending `data: [DONE]` |
| 5 | Runs on GPUs | `POD=$(oc get pod -l app=gemma4-vllm -n eldritchjs-sandbox -o jsonpath='{.items[0].metadata.name}'); oc exec "$POD" -n eldritchjs-sandbox -- nvidia-smi` | **both** H100s show the vLLM process, ~76GB/81.5GB used each (confirms TP=2) |

**Overall PASS = checks 1–3 and 5.** Reference run: all passed; GPU 0 = 76147 MiB,
GPU 1 = 75897 MiB in use. (See `TESTING.md` for the self-serve/colleague copy.)

### Optional scenarios

**Quantized single-GPU (`config.quantized.conf`).** Same `test.sh` checks, but
`GPU_COUNT=1`/`TP_SIZE=1`, so check 5 shows **one** H100 with the vLLM process
(w4a16 weights + KV cache well under 80 GB). Run the whole lifecycle with
`CONFIG_FILE=config.quantized.conf` on `up.sh`/`test.sh`/`down.sh`. Pass condition:
`/v1/models` still lists `gemma-4` and inference is coherent — proving the
compressed-tensors checkpoint is auto-detected and served on a single GPU.

**Autoscaling (kserve, `MAX_REPLICAS > MIN_REPLICAS`).** Deploy e.g.
`CONFIG_FILE=config.quantized.conf MAX_REPLICAS=2 ./up.sh --mode kserve`, then:

| # | Check | Command | Pass condition |
|---|---|---|---|
| A1 | HPA exists | `oc get hpa -n eldritchjs-sandbox` | an HPA `gemma4-predictor` with target `MIN`–`MAX` replicas |
| A2 | Scale-out under load | run `./benchmark.sh --mode kserve` while `oc get pods -l serving.kserve.io/inferenceservice=gemma4 -w` | replica count rises above `MIN_REPLICAS` as the metric passes `SCALE_TARGET` (needs `MAX_REPLICAS × GPU_COUNT` schedulable GPUs) |
| A3 | Scale-in when idle | stop the load and wait (HPA stabilization window) | replicas settle back toward `MIN_REPLICAS` |

Note the honest caveat: RawDeployment's HPA scales on **CPU/memory** (metrics-server
only). It demonstrates the mechanism; the production LLM signal
(`vllm:num_requests_running` via KEDA, or concurrency/RPS via Knative) needs extra
platform components and is out of scope here (§7).

> `CONFIG_FILE=config.quantized.conf MAX_REPLICAS=2 ./up.sh --mode kserve`. Seed
> completed in 89s; predictor Ready on **1** H100 (vLLM log

> `test.sh --mode kserve --stream --gpu` passed **5/5** (single H100 visible).
> **A1** HPA `gemma4-predictor` present (min 1 / max 2, cpu@60%). **A2** under a
> guidellm sweep the GPU-bound model held CPU ~16% (below 60% — the documented
> caveat), so `scaleTarget` was lowered to 12 via the InferenceService (the same
> knob `SCALE_TARGET` sets); KServe propagated it and the HPA fired
> `SuccessfulRescale → New size: 2`. The 2nd replica scheduled on the second GPU
> (separate node), loaded, and reached `1/1` serving — confirming TP=1 lets 1→2
> fit in 2 GPUs. Restoring the target + stopping load returned it toward min.
> Full teardown verified **0 GPUs held**. (Observed: 2nd-replica cold start ~4.5
> min, dominated by a fresh per-pod `torch.compile` — the compile cache is a
> per-pod emptyDir, not shared across replicas. Addressed by the shared compile
> cache below.)

**Shared torch.compile cache (kserve, 2026-09-04).** The ServingRuntime now mounts

> **Reference run (2026-09-04):** dedicated PVC `gemma4-compile-cache` (20Gi, RWX)

> their plain edge Routes. Root cause not yet isolated (istiod VirtualService push /
> SNI match on `knative-ingress-gateway` are the prime suspects).

## 5. Issues encountered and fixes (record for the test plan)
| Symptom | Root cause | Fix |
|---|---|---|
| `model type 'gemma4' not recognized` | transformers too old in generic image | use `:gemma4` tag (transformers ≥ 5.5.0) |
| `ImageInspectError: short name mode is enforcing … ambiguous` | CRI-O short-name enforcement | fully-qualify image `docker.io/vllm/vllm-openai:gemma4` |
| CrashLoopBackOff, `PermissionError … '/.cache'` | OpenShift random UID, `HOME=/` not writable | set `HOME=/home/vllm` on a writable emptyDir |
| DNS failure to `cdn-lfs.huggingface.co` in a probe | dead legacy CDN hostname | none needed — real weights come from `us.aws.cdn.hf.co` |
| Repo not found for `gemma-4-31b-it` | HF repo ids are case-sensitive | use exact `google/gemma-4-31B-it` |
| lazy rollout marked "exceeded progress deadline" mid-download (pod actually fine) | default `progressDeadlineSeconds=600` < cold-start (image pull + 62 GB weights) | set `progressDeadlineSeconds: 1800` on the Deployment |
| **kserve** seed Job: `RuntimeError: ... Permission denied` in `xet_get` | HF **Xet** download backend writes a chunk cache under `$HF_HOME`/`$HOME`; pod's `HOME=/` isn't writable (Xet is separate from `hf_transfer`, so disabling that didn't help) | point `HF_HOME` at the PVC and `HOME` at `/tmp` in the seed Job |
| **kserve** predictor: `executable file 'python' not found in $PATH` | vLLM image ships `python3` (no `python` symlink) | ServingRuntime `command: [python3, -m, vllm...]` |
| **kserve** predictor CrashLoop, `PermissionError ... '/.cache'` | same random-UID/unwritable-`HOME` issue, now in the ServingRuntime | set `HOME=/home/vllm` on a writable emptyDir in the ServingRuntime |
| **kserve** InferenceService "Ready" but endpoint unreachable / `test.sh` dies with no route | up.sh created the Route under `2>/dev/null \|\| true`, hiding a failure | guard the create (check-then-create) so a real error surfaces via `set -e` |
| `huggingface-cli download` fails under `set -eu` in the image | `huggingface-cli` is deprecated and non-functional in the vLLM image | use `hf download` (huggingface_hub) instead |
| guidellm (`:latest`/`:stable`) `Error: No such command 'benchmark'` | current guidellm replaced the `benchmark --target/--processor/--rate-type/--data prompt_tokens=...` CLI with `run --backend kind=... --profile kind=... --data kind=synthetic_text,... --tokenizer kind=huggingface_auto,...` | rewrote `benchmark-pod.yaml` to the `run` CLI; validated live (10-benchmark sweep, exit 0) |
| guidellm writes `benchmarks.{json,csv}` but the run errors on the output dir | default results dir `/results` isn't writable under the random UID | set `GUIDELLM__DEFAULT_RESULTS_DIR=/tmp` |
| **kserve** predictor stuck `ContainerCreating` ~10 min (volume attached, no `FailedMount`, no image pull) after adding a shared compile-cache mount | mounted the **same** `model-cache` claim read-write *and* read-only (via storageUri) in one pod → conflicting mounts wedge the kubelet | give the compile cache its **own** RWX PVC (`gemma4-compile-cache`), not a 2nd reference of the weight claim |

## 6. Teardown (stop GPU/storage charges)

This test is expected to be run repeatedly, so there are two teardown modes.

**Scripted:**
```
cd scripts
./down.sh                # FULL: releases GPUs AND deletes the weight cache
./down.sh --keep-cache   # releases GPUs, KEEPS model-cache PVC (fast re-run)
```
`down.sh` deletes the compute for **all three** modes unconditionally
(Deployment/Service/Route for `lazy` *and* InferenceService/ServingRuntime/seed
Job/external Service/Route for `kserve`/`serverless`), removes the hashed params ConfigMap, the
`hf-token` secret, and any leftover benchmark Job, optionally the PVC, then
verifies **0 GPUs held**. It is mode-agnostic on purpose — you do **not** need to
pass the `SERVE_MODE` you deployed with, and running it with the wrong mode can no
longer leave a predictor holding GPUs while deleting the shared PVC. The manual
equivalents follow.

### 6a. Full teardown (default — releases GPUs *and* storage)
Use between test cycles when you don't need to preserve anything.
```
# lazy:
oc delete deploy,svc,route,pod -l app=gemma4-vllm -n eldritchjs-sandbox --ignore-not-found
```

### 6b. Fast re-run teardown (releases GPUs, **keeps** the weight cache)

compute-delete lines from 6a for your mode, but **leave `pvc/model-cache` in
place** — i.e. just `./down.sh --keep-cache`.

## 7. Out of scope for this test (would be needed for a real deliverable)
- **Auth/TLS**: endpoint is open with the default router cert (`curl -k`). Add an
  API gateway / auth and a real cert for anything shared.
- **Serving path**: a plain Deployment + Route (`lazy`), a KServe RawDeployment
  InferenceService (`kserve`), and a Knative Serverless InferenceService
  (`serverless`) are all implemented. Autoscaling **is** wired and validated in
  `kserve` (RawDeployment HPA on CPU/memory) and `serverless` (Knative KPA on
  concurrency/RPS, incl. scale-to-zero — see §4 Optional scenarios). Remaining out
  of scope: the CPU-independent HPA signal `vllm:num_requests_running` via KEDA;
  canary/revisions and model-registry integration. **Also unfinished:** the
  `serverless` client-facing endpoint does not route cleanly through this cluster's
  net-istio mesh edge (the autoscaler works; the 200 through the mesh is cluster
  plumbing — see §4 caveat).
- **Multi-model**: one model per vLLM server here. Multiple models = N servers, or
  MIG/time-slicing to pack several onto fewer GPUs.
- **RDMA/SR-IOV networking**: not configured on this cluster (no SR-IOV operator,
  no VF resources). Not needed for single-node TP serving; would matter for
  multi-node training/inference.
